PostgreSQL が RDB の中で突出して見える理由

AWS や GCP を使うほど、「同じ SQL を、マネージドで、拡張付きで、クラウド間でも動かせる」エンジンが PostgreSQL に集約されているのが分かります。ここでは投資判断ではなく、機能の地図としてまとめます。

このページは静的な解説です。データベースには接続しません。クラウド製品の細部はバージョンで変わるので、本番採用前に各社のドキュメントを確認してください。

1. 全体像 — 「RDBコア × 拡張 × クラウド実装」

MySQL が「Web向けの速いエンジン」、Oracle が「巨大な製品スイート」だとすると、PostgreSQL は 標準SQLのRDBを核に、型・索引・拡張で領域を足せるプラットフォームです。クラウド各社は互換レイヤを自前で抱えつつ、プロトコルと SQL は PostgreSQL に寄せています。

マネージドの第一選択肢が PG RDS、Aurora PostgreSQL、Cloud SQL、AlloyDB が同じ方言に寄る Oracle はライセンス、MySQL はフォーク差（Aurora MySQL 等）が大きい

2. ベース RDB としての強さ

拡張の話の前に、素の PostgreSQL がすでに「厳しい RDB」です。トランザクション、制約、SQL、索引の四つが揃っていることが、JSON や GIS を足しても破綻しない理由です。

トランザクションと同時実行

MVCC なので、長い SELECT が INSERT/UPDATE を止めません。DDL もトランザクションに載せられ、失敗したらロールバックできます（多くの MySQL DDL は非トランザクション）。セーブポイント、直列化可能な分離レベル、制約の遅延チェックが使えます。

制約が「データモデル」になる

PK / FK / UNIQUE / NOT NULL / CHECK に加え、EXCLUDE（期間の重なり禁止など）があります。部分 UNIQUE（WHERE 付きのユニーク索引）で「有効行だけ一意」も表現できます。JSON を置いても、生成列経由で同じ制約を掛けられます。

SQL と索引 — コアだけで足りる範囲が広い

Spanner や CockroachDB は「グローバル書き込み」では勝つことがあります。それらは PostgreSQL 互換をうたっていても、制約・拡張・トランザクションの意味がずれるので、別種として扱うのが安全です。

3. JSON 型でありながら、正規化して扱える

ここが「ドキュメント DB を別建てしなくてよい」最大の理由です。JSONB は schemaless に見えて、生成列・制約・外部キー・GIN で関係モデルに接続できます。最初はゆるく置き、ホットなキーだけ列に昇格する、という段階設計が SQL のままできます。

表4. json / jsonb / 普通の列の使い分け
json jsonb 関係列（正規化）
保存 入力テキストをほぼそのまま 分解したバイナリ。キー順は正規化される 型どおり。NULL と制約が明確
検索・索引 ほぼ向かない GIN、JSONPath、包含 @> B-Tree が最速で計画も読みやすい
制約 CHECK で jsonb 関数を書く程度 生成列経由が本命 FK / UNIQUE / CHECK がそのまま
向くデータ 監査で原文が欲しいとき キーが変動する属性、イベント、外部 API の余り 結合・集計・金額・ステータスなど契約になった項目 
-- ペイロードは残し、関係として扱うキーだけ型を付ける
CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  payload jsonb NOT NULL,
  customer_id uuid GENERATED ALWAYS AS ((payload->>'customer_id')::uuid) STORED,
  status text GENERATED ALWAYS AS (payload->>'status') STORED,
  amount integer GENERATED ALWAYS AS ((payload->>'amount')::integer) STORED,
  CONSTRAINT orders_status_chk CHECK (status IN ('draft', 'paid', 'void')),
  CONSTRAINT orders_amount_chk CHECK (amount >= 0),
  CONSTRAINT orders_customer_fk FOREIGN KEY (customer_id) REFERENCES customers (id)
);
CREATE INDEX orders_payload_gin ON orders USING gin (payload jsonb_path_ops);
CREATE INDEX orders_customer_idx ON orders (customer_id);

運用のコツ: JSONB のキーをアプリが勝手に増やし続けると、生成列が追い付きません。「列にする条件」（検索する、結合する、金額として集計する）を先に決めると、ドキュメント DB 化を防げます。

4. 拡張機能 — 別製品を増やさずに領域を足す

CREATE EXTENSION が、クラウドで「チェックを入れる」操作になるのが大きいです。GIS・あいまい検索・監査・ベクトル検索を、同じトランザクションとバックアップ境界の中に置けます。

5. スケールの容易性 — 楽な段と、急に難しくなる段

PostgreSQL のスケールは「読み取りと容量はクラウドがかなり楽、書き込みの水平分割は今でも難しい」が正直な地図です。AWS/GCP を使うほど、この段差が製品機能として見えます。

6. 移行の容易性 — 「同じエンジン」をクラウドが量産している

PostgreSQL が強いのは機能表だけでなく、持ち出せることです。ワイヤプロトコルと pg_dump がオープンで、AWS も GCP も「PostgreSQL 互換」を商品にしているので、移行の道具が流用できます。

表7. 移行手段
手段 停止時間 向くケース 注意
pg_dump / restore サイズに比例して長い 小さい DB、スキーマ検証、開発コピー 権限・拡張・照合順序を先に合わせる
物理バックアップ（pg_basebackup 等） 短いがメンテは必要 同一メジャー、近い環境 マネージドでは使えないことが多い
論理レプリケーション（pub/sub） 切り替えを秒〜分にできる PG→PG のオンライン移行、バージョン上げ DDL、シーケンス、大きな LOB、スロット肥大
AWS DMS / GCP DMS 設計次第 他エンジンから、または運用を委託 型マッピング、トリガ、無停止の幻想に注意
postgres_fdw で段階移行 表単位 サービスを分割しながら移す 結合の性能、分散トランザクションは期待しない

移行が「容易」な条件: 拡張が先方にある、ICU 照合を揃える、superuser 前提の処理を捨てる、Aurora/AlloyDB 固有機能に依存しない。逆に、ストアドで業務を固めた Oracle からの移行は SQL 以前に業務の移植です。

7. 接続の安全性 — パスワードをアプリから追い出すまで

PostgreSQL 自体の認証（SCRAM、クライアント証明書、ロール）と、クラウドの IAM・プロキシ・プライベートネットが重なると、「接続文字列に長期秘密を書かない」形が現実的になります。さらに RLS で行まで閉じられます。

表8. 認証・認可の部品
層 PostgreSQL 本体 AWS GCP
認証 SCRAM-SHA-256、クライアント証明書、pg_hba IAM データベース認証、Secrets Manager 回転 IAM データベース認証、Secret Manager
接続の出し方 libpq、sslmode=verify-full RDS Proxy、IAM トークン Cloud SQL Auth Proxy / 言語コネクタ、AlloyDB Auth Proxy
ネットワーク listen_addresses、ホストベース VPC、SG、PrivateLink VPC、PSC、Private IP、VPC SC
認可 ROLE、GRANT（表・列）、RLS、SECURITY BARRIER VIEW IAM は接続まで。中の表権限は SQL 同様。IAM と SQL 権限は別物
監査・暗号 pgaudit、pgcrypto（補助） 保存時暗号は KMS、CloudTrail と併用 CMEK、Cloud Audit Logs と併用

IAM 認証は「ログインできた」だけで、SELECT の範囲は RLS と GRANT です。プロキシを挟むとクライアント IP が全部プロキシに見えるので、pg_hba を IP 頼りにしない方がよいです。

両クラウドとも「PostgreSQL を核に、ストレージとプロキシだけ自社実装」という形に収束しています。アプリの SQL をあまり変えずに、可用性の上げ方だけ製品を選べます。

AWS で「PG が本命」に見えるとき

Aurora の MySQL 版と PostgreSQL 版を比べると、拡張・JSON・制約・移行の持ち出しやすさで PostgreSQL 版に寄ることが多いです。RDS Proxy と IAM 認証が、接続数と秘密管理の両方を同時に解きます。

GCP で「PG が本命」に見えるとき

Cloud SQL で足りなければ AlloyDB に上げても、アプリは libpq のままです。Auth Proxy がローカルでも GKE でも同じパターンになり、BigQuery は倉庫として横に置く（置き換えない）使い分けがはっきりします。

覚え方（1文）

Cloud SQL は「普通の PostgreSQL」、Plus は「止まらない普通の PostgreSQL」、AlloyDB は「速い PostgreSQL」、AlloyDB マルチリージョンは「速い PostgreSQL の読み取りと DR を他リージョンへ」、Spanner マルチリージョンは「PostgreSQL ではなくグローバル書き込み機」に PG の顔を付けたもの。

ひっかけ

「マルチリージョン」と書いただけでは AlloyDB と Spanner を同じにしない。secondary への書き込み、99.999%、リージョン喪失後の自動書き込み継続、のいずれかがあれば Spanner。拡張・列指向・ベクトルがあれば AlloyDB。99.99% とメンテ込みだけで HTAP の話が無ければ Cloud SQL Plus で足りることが多い。

投資アドバイスではなく試験用の機能地図です。SLA の適用条件（HA 有効、read pool 2 ノード以上、対象リージョンなど）を満たさない構成は数字どおりになりません。

まとめ: PostgreSQL の強さは「RDB の約束（制約・トランザクション・SQL）を捨てずに、JSON・GIS・ベクトル・監査を同じバックアップ単位に足せる」ことです。AWS と GCP はその核を壊さずに、接続・ディスク・フェイルオーバーだけを製品化したので、使うほど差がはっきりします。
